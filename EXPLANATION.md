# Устройство проекта и соответствие заданию

## Классы и связи

| Файл | Назначение |
|---|---|
| `Main.java` | Создаёт окно и объекты на EDT, связывает их ссылками, запускает движок |
| `GameConfig.java` | Интерфейс констант: геометрия, скорость, цвета, клавиши, длительность бонуса |
| `GameEngine.java` | Игровая модель, столкновения, счёт, жизни, уровни, бонусы; реализует `Runnable` |
| `GamePanel.java` | Наследник `JPanel`, рисует фон, объекты, счёт, подсказки и состояние |
| `GameController.java` | Реализует `MouseMotionListener`, `MouseListener`, `KeyListener`, `WindowListener` |
| `Brick.java` | Координаты, ряд и прочность отдельного блока |

`GamePanel` хранит ссылку на `GameEngine`, а движок хранит ссылку на панель для `repaint()`. Обработчик получает ссылки на движок, панель и окно. Глобального статического экземпляра игрового состояния нет. Поля классов закрыты; состояние представления выдаётся неизменяемым снимком. Вложенные `record` описывают снимок и его элементы, а `enum` — состояния игры.

## Потоки

Окно и обработчики Swing работают в Event Dispatch Thread. `Main.main()` передаёт создание интерфейса в `SwingUtilities.invokeLater()`.

Отдельный `Thread` с именем `neon-breaker-loop` запускает `GameEngine.run()`. Цикл измеряет прошедшее время через `System.nanoTime()`, обновляет физику, вызывает `repaint()` и выполняет `Thread.sleep(FRAME_MS)`. Цель — около 120 обновлений в секунду; точное число зависит от планировщика ОС. Скорость движения рассчитывается через прошедшее время, а не число кадров.

Методы изменения и чтения модели синхронизированы на одном объекте `GameEngine`. В `snapshot()` создаются неизменяемые копии списков. Отрисовка использует эти копии после освобождения блокировки, поэтому не читает изменяющуюся коллекцию. Сам `repaint()` безопасно вызывается из рабочего потока: Swing планирует рисование на EDT.

Повторный `start()` не создаёт второй поток. При закрытии окна вызывается `stop()`: флаг `running` сбрасывается, поток прерывается и выходит из цикла. При `InterruptedException` флаг прерывания восстанавливается. Перезапуск партии не требует создания нового потока.

## Физика

1. Мяч имеет координаты и компоненты скорости `velocityX`, `velocityY`. Позиция изменяется на `velocity * dt`.
2. Длительный кадр ограничивается 40 мс, а обновление делится на четыре подшага. При предельной скорости мяч перемещается за подшаг не более чем на 5,5 пикселя, меньше толщины платформы и блока. Это уменьшает риск прохождения сквозь объекты.
3. Левая, правая и верхняя границы исправляют координату мяча и отражают соответствующую компоненту скорости.
4. Удар по платформе обрабатывается только при движении вниз и пересечении её верхней границы. Смещение мяча от центра платформы определяет угол отскока; вертикальная скорость всегда направлена вверх, поэтому мяч не застревает в горизонтальном движении.
5. Для столкновения с блоком ищется ближайшая к центру мяча точка прямоугольника. Расстояние до неё сравнивается с радиусом. Предыдущее положение мяча определяет сторону отражения; после удара мяч выносится за грань блока.
6. Одно столкновение уменьшает прочность на единицу и увеличивает счёт на 10. При нулевой прочности блок перестаёт участвовать в физике и отрисовке.
7. Если мяч целиком прошёл нижнюю границу, отнимается одна жизнь и включается ожидание подачи. При нуле жизней устанавливается `LOST`. Пустой последний уровень устанавливает `WON`.

Пауза прекращает обновление физики, бонуса и его таймера. Платформа ограничивается границами с учётом текущей ширины, в том числе при получении бонуса у края. Новая партия очищает счёт, уровни, бонусы и след мяча.

## Состояния

| Состояние | Что происходит | Переход |
|---|---|---|
| `READY` | Мяч прикреплён к платформе | Пробел / щелчок → `PLAYING` |
| `PLAYING` | Обновляются физика и бонусы | P → `PAUSED`; пропуск → `READY` / `LOST`; очистка → следующий уровень / `WON` |
| `PAUSED` | Игровое время остановлено | P → `PLAYING` |
| `WON` | Показана победа, физика остановлена | N → новая партия |
| `LOST` | Показано поражение, физика остановлена | N → новая партия |

N из любого состояния запускает новую партию. Закрытие окна и Esc завершают приложение.

## Выполненная проверка

Сборка выполнена JDK 17 с целевой версией Java 17 и флагом `-Xlint:all`, без предупреждений. Скрипты сборки и тестов выполнены в Windows. Проверки прошли на Java 17 и Java 21. Готовый JAR отдельно запущен: создано окно «Neon Breaker | Java Swing», ошибок в stderr нет; после проверки тестовый процесс остановлен.

В `GameEngineTest` прошло 32 утверждения: начальное состояние, ограничение платформы, привязка мяча, подача, пауза/продолжение, три стенки, отскок от центра/края платформы, начисление очков и удаление блока, боковое столкновение, потеря каждой жизни, поражение, сброс партии, выпадение/получение/окончание/пропуск бонуса, следующий уровень, прочный блок, победа, неподвижность после победы, запуск и завершение потока.

Тестовые координаты для точных столкновений задаются через reflection только в тесте; открывать приватные поля производственного кода ради проверок не потребовалось. Рисование `GamePanel` также выполнено на EDT в изображение: проверены начальное и активное состояние, читаемость текста и отсутствие обрезки. Это отрисовка настоящего Swing-компонента, а не макет.

Интерактивная проверка живого окна инструментом управления рабочим столом не выполнена: инструмент не смог инициализироваться. Автотесты модели и проверка изображения не заменяют проверки реальной мышью и клавиатурой.

## Что проверить перед сдачей

1. Открыть `START.cmd`, подвигать мышью и убедиться, что платформа не выходит за поле.
2. Нажать пробел, затем P: мяч должен остановиться. Повторное P продолжает игру.
3. Подать мяч щелчком, проверить N и выход по Esc.
4. Несколько раз пропустить мяч: счётчик жизней уменьшается и появляется поражение.
5. При необходимости изменить палитру и скорости через `GameConfig`, затем запустить `BUILD.cmd`.

## Краткое объяснение для обсуждения работы

«Проект представляет собой арканоид с тремя уровнями. Модель хранится в GameEngine, GamePanel только рисует, а GameController принимает ввод через стандартные интерфейсы событий. Параметры собраны в интерфейсе GameConfig. Движок реализует Runnable и работает в отдельном потоке, который регулируется Thread.sleep. Swing рисует на EDT. Для согласованного доступа используются synchronized и неизменяемые снимки. Угол отскока зависит от точки попадания в платформу; каждый седьмой разрушенный блок может дать расширяющий бонус. Победа наступает после очистки всех уровней, поражение — после потери трёх жизней».

Перед сдачей стоит самостоятельно разобрать `stepBall`, `hitBrick` и `snapshot`: в них находятся основные алгоритмы проекта.
